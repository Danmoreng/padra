GTX 1070: automatic follow-up cache and Sternenwrack benchmark, 2026-11-05

Result

Stateless full-history Chat requests and Responses requests without a retained
root now automatically reuse a compatible resident GPU prefix checkpoint.
Previously the server only selected the existing checkpoint through an explicit
session lease; unmodified Pi sends full history without a session ID.

The real-GPU tests and fixed Pi replay pass. Three unchanged requests take
35.189 s with reuse versus 52.067 s with a fresh namespace on every request
(32.42% less wall time). All normalized outputs, reasoning, tool names/arguments,
finish reasons and token counts are identical, including comparison to the
pre-change binary. GPU memory remains 7311 MiB sampled peak, about 7.14 GiB.

The full coding task remains unsuccessful on Padra: the fourth model call
aborts with invalid_tool_output while attempting to write game.js. Caching reduces
time to that same failure from 119.051 s to 92.290 s; this is not a successful
task time.
llama.cpp finishes its agent trajectory after 748.789 s, but its generated game
has significant functional defects. Neither result establishes a successful
completion-time winner or general coding-quality ranking.

Fixed-request performance

Each engine receives the same three captured request bodies, byte for byte.
No model-generated tools are executed during this replay. Padra performs three
cold requests with unique credential namespaces, then three with one namespace.
llama.cpp performs one normal resident sequence in a fresh server. The slightly
different rendered token counts below are preserved, not treated as identical
tokenized prompts. Authorization namespaces are a Padra cache-isolation policy;
they are not a llama.cpp cache-flush mechanism.

Total Padra prefill falls 29.0191 -> 12.1212 s. Decode remains 22.9938 -> 23.0337 s;
the benefit comes from avoiding repeated prompt work, not faster decoding.

First cold request, both 2756 input tokens: Padra 314.8 tok/s prefill,
llama.cpp 496.5 tok/s. Across all three resident requests, aggregate decode is

Cache semantics and validation

There is one resident checkpoint, scoped to the loopback credential namespace.
Anonymous loopback requests share a namespace. Explicit sessions and stateless
requests retain separate ownership. Exact canonical token-prefix, runtime,
generation, capacity and format checks are authoritative. Changed prefixes,
owners, stale handles or intervening explicit sessions safely replay history.
No implicit logical session or response record is created for store:false.
Partial tools, execution failure and running cancellation invalidate retained
ownership; cancellation while queued preserves an untouched checkpoint.
SM61 retains complete 256-token expert chunks, preserving existing arithmetic.
This currently reuses a prompt checkpoint, not an arbitrary multi-session cache
or the whole previously generated continuation. Small sub-chunk histories may
therefore show zero cached tokens even though automatic caching is enabled.
