Recommended next work, with separate measured changes
1. Prefill: profile the current K3 path, then add a 2048-key attention graph
   between the existing 1024/4096/8192 tiers. For 1025-2048 actual tokens,
   global attention currently computes a 4096-key matrix and masks the tail.
   Reduce unnecessary gather, QK, softmax and PV work. Keep chunk256 prefix
   boundaries, graph admission/reserve and accurate capture inventory.
   Changing GEMM dimensions may change rounding: rerun frozen logits/NLL,
   executable code tasks and cache/MTP equivalence before retaining it.
2. Decode/MTP: port the two-row Q8 verifier attention to the SIMT runtime,
   using the SM61 synchronous staging path and its existing split counts.
   Preserve the overwritten local-ring row, active-row/end-of-budget checks,
   rollback, prefix restore and sequential numerical partition. Validate
   wrap boundaries and cancellation before measuring launch savings.
   Then measure D1/D2/D3 on coding prompts; more proposals can cost more than
   they save. Keep depth 1 until an end-to-end gain is demonstrated.
3. Further expert/KV work: use operator timings and profiler traces to choose
   the remaining bottleneck. Prefer weight reuse across verified rows and
   fewer repeated Q8 KV conversions if measured costs justify them. Avoid
   permanently expanded weight/cache copies that defeat the 8 GiB target.
4. Main integration: fix the formatter failures in a separate mechanical
   commit; keep approximate DP4A opt-in and its quality identity explicit.
   Re-run CUDA-off/native-text/SDK CI plus SM61 default and DP4A builds.
   Run SM120 regression checks on the other machine for shared CUDA headers,
   Q8 attention, prefix snapshots and MTP. Review the large backend addition
   separately from optional performance changes; attach current measurements
   and bounded qualification evidence to the eventual PR.

Acceptance for each optimization: same pinned models and sampling settings;
uncached prefill, warm prefix hits and decode measured separately; paired or
interleaved baseline/candidate runs; exactness where promised, quality gates
for changed arithmetic; positive end-to-end benefit and maintained memory
reserve. Reaching llama.cpp parity is a performance objective, separate from
establishing a correct, clearly scoped experimental Pascal backend in main.
